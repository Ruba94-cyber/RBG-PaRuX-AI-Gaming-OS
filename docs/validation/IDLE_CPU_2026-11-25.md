# Idle CPU, before and after adaptive polling (2026-11-25)

Harness: `tools/competitor-bench/Measure-AppIdleCpu.ps1` (CPU TIME deltas of `PaRuX` + `PaRuX.Server` over 120 s after a 45 s settle, `PARUX_DATA_ROOT` isolated under `.ai/`, 3 runs, release builds of the same tree before and after). Wall-clock is only used to turn seconds into a rate. Machine load is printed with every run (system busy %, number of testhost/msbuild processes); the machine was shared (Claude Desktop, idle build servers, one testhost), busy 9-21%.

| Build | Run 1 | Run 2 | Run 3 | Median | UI / Core CPU s per 120 s |
|---|---|---|---|---|---|
| before (4.5.1 + 54ec61a8) | 4.04% | 3.65% | 3.84% | 3.84% | 0.9-1.25 / 3.4-3.6 |
| after (this branch) | 1.99% | 2.01% | 1.78% | 1.99% | 0.81-0.97 / 1.3-1.6 |

Machine busy during "before": 13.1 / 14.2 / 14.2%; during "after": 18.5 / 18.3 / 15.9% (the after runs had more background load, not less).

## Periodic work, classified (Core `dotnet-trace`, 60 s, idle; UI by source)
| Source | Interval before | Measured cost | Action |
|---|---|---|---|
| Playnite watcher `WindowsProcessSnapshotSource.Capture` | 1 s, full Toolhelp snapshot | about 1.1% of a core (the largest item) | idle: window-based probe every 2 s, full snapshot only every 10 s; once Playnite exists: original 1 s tick |
| Core console logger (routing / Kestrel Information lines) | per HTTP request | about 14% of the Core's sampled CPU | filtered to Warning |
| HTTP polls from the UI: badge timer (2 s, 3 requests), 4 desktop worker pollers (2/3/5/5 s) | about 2.7 requests/s | per request: Kestrel pipeline + `CorporateMode.IsActive` (4 `File.Exists`) | idle 4 s / hidden 6 s, shared task-list snapshot, marker probe cached 10 s |
| Gaming guard (`GamingGuardService`) | 250 ms marker read + reopen sweep | about 0.3% | marker read kept at 250 ms, reopen sweep every 2 s |
| `WorkloadOrchestrator` trigger loop | 1 s | Sunshine install probe (file system) | probe cached 10 s |
| Agent scheduler (`AgentSchedulerHostedService`) | 2 s, several SQLite opens | about 0.1-0.2% | NOT changed (see risks) |
| Temporary game mod recovery | 15 s | negligible | none |
| Knowledge recovery timer | 2 min | negligible | none |
| GPU telemetry / hardware sampler / nvidia-smi | on demand only (no periodic loop found) | none at idle | none |
| UI view timers (PausedGameBanner, DocumentSearch, GameDownloads, ModelTuningStatus) | 2-5 s while the view is shown | UI thread + HTTP | skipped while the window is minimized or in the tray |

## Latency (simulated clock, same tracker and service code)
Time from "Playnite and its game appeared" to the yield entering Gaming (4 s start debounce included): worst case 5.75 s before, 6.00 s after (the 2 s idle tick). With Playnite already running (the normal case for a Playnite user) it is identical to before. The orchestrator's VRAM release itself is unchanged.

## Not measured
Real Playnite, a real game, GPU VRAM release timing, and the installed MSI were not exercised; the numbers come from a headless app with an empty data root and no model.
